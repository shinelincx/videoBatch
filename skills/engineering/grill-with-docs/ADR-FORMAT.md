# ADR 格式

ADR 存放在 `docs/adr/` 目录下，使用顺序编号：`0001-slug.md`、`0002-slug.md`，以此类推。

`docs/adr/` 目录延迟创建——仅在需要第一条 ADR 时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么、我们做了什么决定、为什么。}
```

就这么简单。一条 ADR 可以只有一个段落。其价值在于记录下**做出了**一项决策以及**为什么**——而不是填满各个章节。

## 可选章节

仅在这些章节能带来真正价值时才包含它们。大多数 ADR 不需要这些。

- **Status（状态）** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策可能被重新审视时有用
- **Considered Options（考虑过的方案）**——仅当被否决的替代方案值得记住时才写
- **Consequences（影响）**——仅当存在非显而易见的下游影响需要明确指出时才写

## 编号规则

扫描 `docs/adr/` 目录，找到现有的最大编号，加一即可。

## 何时应该提供 ADR

以下三个条件必须**同时满足**：

1. **难以回退**——后续改变主意的成本相当高
2. **缺少上下文时会令人困惑**——未来的读者看到代码会疑惑"他们当初为什么会这么做？"
3. **经过真实权衡后的结果**——确实存在多种方案，你出于特定原因选择了其中一个

如果一项决策很容易回退，那就跳过——反正以后改了就是。如果不令人困惑，就没人会好奇为什么。如果没有真正的替代方案，那除了"我们做了显而易见的事"之外没什么好记录的。

### 什么情况 qualifies（符合条件）

- **架构形态。** "我们使用 monorepo。""写模型采用 event-sourced，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而非同步 HTTP。"
- **带来锁定效应的技术选型。** 数据库、消息总线、认证提供商、部署目标。不是每个库都要记录——只有那些替换起来需要花一个季度的才值得。
- **边界和范围决策。** "Customer 数据由 Customer 上下文独占拥有；其他上下文只能通过 ID 引用。"明确说"不"的决策和说"是"的一样有价值。
- **刻意偏离常规做法。** "我们选择手写 SQL 而不是用 ORM，因为 X。"任何合理的读者可能会假设相反做法的情况。这能防止下一位工程师去"修复"那些刻意为之的设计。
- **代码中不可见的约束。** "由于合规要求，我们不能使用 AWS。""响应时间必须在 200ms 以内，因为合作方 API 的合同约定。"
- **否决方案，且否决原因并不显而易见。** 如果你考虑过 GraphQL 却出于微妙的原因选了 REST，那就记录下来——否则半年后还会有人再次提议用 GraphQL。
