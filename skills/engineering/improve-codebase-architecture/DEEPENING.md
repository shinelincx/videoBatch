# Deepening（深化）

在给定依赖关系的情况下，如何安全地深化一组浅层模块。假设你已掌握 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**module**、**interface**、**seam**、**adapter**。

## 依赖分类

评估深化候选方案时，对其依赖进行分类。类别决定深化模块如何跨越接缝进行测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。始终可深化——合并模块，直接通过新接口测试。不需要适配器。

### 2. 本地可替代（Local-substitutable）

具有本地测试替身的依赖（PGLite 替代 Postgres、内存文件系统）。如果替身存在则可深化。深化后的模块在测试套件中使用替身运行。接缝是内部的；模块外部接口处没有端口。

### 3. 远程但自有（端口与适配器）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义**端口**（接口）。深化模块拥有逻辑；传输层作为**适配器**注入。测试使用内存适配器。生产使用 HTTP/gRPC/队列适配器。

建议格式：*"在接缝处定义端口，为生产实现 HTTP 适配器，为测试实现内存适配器，这样逻辑就集中在一个深层模块中，即使它部署在网络上。"*

### 4. 真正的外部（模拟）

你无法控制的第三方服务（Stripe、Twilio 等）。深化模块将外部依赖作为注入端口接收；测试提供模拟适配器。

## 接缝规范

- **一个适配器意味着假设的接缝。两个适配器意味着真实的接缝。** 除非至少有两个适配器是合理的（通常是生产 + 测试），否则不要引入端口。单一适配器的接缝只是间接层。
- **内部接缝 vs 外部接缝。** 深层模块可以有内部接缝（对其实现私有，供自身测试使用）以及接口处的外部接缝。不要因为测试使用了内部接缝就通过接口暴露它们。

## 测试策略：替换，而非叠加

- 一旦深层模块接口处存在测试，浅层模块的旧单元测试就变成浪费——删除它们。
- 在深层模块的接口处编写新测试。**接口即测试面。**
- 测试通过接口断言可观察的结果，而非内部状态。
- 测试应能在内部重构中存活——它们描述行为，而非实现。如果实现变更时测试也必须修改，那测试就越过了接口。
