# Logic Prototype（逻辑原型）

一个小型交互式终端应用，让用户手动驱动状态模型。当问题涉及**业务逻辑、状态转换或数据形状**时使用——那种在纸上看起来合理，但只有推入真实案例后才能感觉出问题的东西。

## 什么时候选择这个形态

- "我不确定这个状态机是否处理了 X 然后 Y 的边界情况。"
- "这个数据模型真的能让我表达那种……的情况吗？"
- "在写正式 API 之前，我想感受一下 API 应该长什么样。"
- 任何用户想要**按按钮、观察状态变化**的场景。

如果问题是"这个应该长什么样"——选错了分支。使用 [UI.md](UI.md)。

## 流程

### 1. 明确问题

在写代码之前，用一段话写下你要原型化的状态模型和问题。写在原型的 README 或文件顶部注释中。回答错误问题的逻辑原型是纯浪费——明确问题以便后续验证，无论用户是否在线。

### 2. 选择语言

使用宿主项目使用的语言。如果项目没有明显的运行时（例如文档仓库），询问用户。

匹配项目现有的工具约定——不要仅仅为了原型引入新的包管理器或运行时。

### 3. 将逻辑隔离到可移植模块

将核心逻辑——回答问题的部分——放在一个小型、纯净的接口后面，以便后续可以提取并放入正式代码库。围绕它的 TUI 是一次性的；逻辑模块不应该是一次性的。

正确的形态取决于问题：

- **纯 reducer**——`(state, action) => state`。适合动作是离散事件、状态是单一值的情况。
- **状态机**——显式的状态和转换。适合"现在哪些动作甚至合法"本身就是问题一部分的情况。
- **一组纯函数**作用于纯数据类型。适合没有隐式当前状态、只有转换的情况。
- **具有清晰方法表面的类或模块**，当逻辑确实拥有持续的内部状态时。

选择最适合所问问题的形态，_而非_最容易连接 TUI 的形态。保持纯净：没有 I/O、没有终端代码、没有用 `console.log` 做控制流。TUI 导入它并调用它；没有反向依赖。

这使得原型超出自身生命周期后仍然有用。当问题被回答后，经过验证的 reducer/状态机/函数集可以提升到正式模块中——TUI 外壳被删除。

### 4. 构建能暴露状态的最小 TUI

构建为**轻量级 TUI**——每次刷新时，清屏（`console.clear()` / `print("\033[2J\033[H")` / 等价操作）并重新渲染整个帧。用户应该始终看到一个稳定的视图，而不是无限增长的滚动历史。

每帧包含两部分，按此顺序：

1. **当前状态**，以漂亮的格式输出，便于对比（每行一个字段，或格式化的 JSON）。字段名或节标题使用**粗体**，不太重要的上下文（时间戳、ID、派生值）使用**暗淡**。原生 ANSI 转义码即可——`\x1b[1m` 粗体、`\x1b[2m` 暗淡、`\x1b[0m` 重置。除非项目中已有样式库，否则不需要引入。
2. **键盘快捷键**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 时钟跳动  [q] 退出`。粗体键名、暗淡描述，或反过来——以清晰可读为准。

行为：

1. **初始化状态**——一个内存中的单一对象/结构体。启动时渲染第一帧。
2. 每次读取**一个按键（或一行）**，分派到改变状态的处理器。
3. 每次操作后**重新渲染**整个帧——不要追加，要替换。
4. **循环直到退出。**

整个帧应该能放在一个屏幕内。

### 5. 让它可一条命令运行

在项目现有的任务运行器中添加脚本（`package.json` scripts、`Makefile`、`justfile`、`pyproject.toml`）。用户应该能运行 `pnpm run <prototype-name>` 或等价命令——永远不需要记住路径。

如果宿主项目没有任务运行器，直接把命令写在原型的 README 顶部。

### 6. 交给用户

给用户运行命令。他们会自己驱动；有趣的时刻是当他们说"等等，这不应该可能发生"或"咦，我以为 X 会不同"——这些就是_想法_中的 Bug，而这正是原型的全部意义。如果他们想添加新动作，就添加。原型是演进的。

### 7. 捕获答案

当原型完成任务后，问题的答案是唯一值得保留的东西。如果用户在线，询问他们学到了什么。如果不在线，在原型旁边留下 `NOTES.md`，以便在原型被删除之前填写答案（或如果你观察了整个会话，由你填写）。

## 反模式

- **不要添加测试。** 需要测试的原型不再是原型。
- **不要连接真实数据库。** 使用内存存储，除非问题明确涉及持久化。
- **不要泛化。** 不要考虑"如果我们以后想支持 X 怎么办"。原型只回答一个问题。
- **不要把逻辑和 TUI 混在一起。** 如果 reducer/状态机引用了 `console.log`、提示或终端转义码，它就不再可移植。保持 TUI 作为纯净模块上的薄壳。
- **不要把 TUI 外壳带到生产中。** 外壳是为了在终端中手动驱动而优化的。它背后的逻辑模块才是值得保留的部分。
