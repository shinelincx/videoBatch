# UI Prototype（UI 原型）

在单个路由上生成**多个截然不同的 UI 变体**，通过底部浮动栏切换。用户在浏览器中快速切换变体，选择一个（或从每个中偷取一些元素），然后扔掉其余的。

如果问题涉及逻辑/状态而非外观——选错了分支。使用 [LOGIC.md](LOGIC.md)。

## 什么时候选择这个形态

- "这个页面应该长什么样？"
- "在正式确定之前，我想看看这个仪表盘的几种选项。"
- "为设置页面试试不同的布局。"
- 任何用户原本要花一整天在脑海中挑选三个模糊模型的场景。

## 两种子形态——强烈推荐子形态 A

当 UI 原型**与应用的其余部分相邻**时更容易评判——真实的头部、真实的侧边栏、真实的数据、真实的密度。独立的一次性路由是真空中的存在：每个变体在隔离状态下看起来都不错。只要存在合理的现有页面来承载变体，就默认选择子形态 A。仅当原型确实没有附近可挂载的地方时才选择子形态 B。

### 子形态 A — 对现有页面的调整（首选）

路由已存在。变体在**同一路由**上渲染，通过 `?variant=` URL 搜索参数控制。现有的数据获取、参数和认证全部保留——只有渲染部分切换。这是默认选择；除非有特殊理由，否则选它。

如果原型要做的东西还没有页面，但_自然应该属于某个页面的一部分_（仪表盘的新区域、设置页面的新卡片、现有流程的新步骤）——这也属于子形态 A。在宿主页面内挂载变体。

### 子形态 B — 新页面（最后手段）

仅当被原型化的东西确实没有现有页面可以挂载时才使用——例如全新的顶级表面，或无法嵌入任何合理位置的流程。

创建一个**一次性路由**，遵循项目已有的路由约定——不要发明新的顶层结构。命名要让人一眼看出是原型（例如在路径或文件名中包含 `prototype`）。使用相同的 `?variant=` 模式。

在确定使用子形态 B 之前，再次确认：真的没有现有页面可以嵌入吗？空路由会隐藏填充良好的路由能暴露的设计问题。

两种子形态中，底部浮动栏是相同的。

## 流程

### 1. 明确问题并确定数量 N

默认 **3 个变体**。超过 5 个就不再是截然不同的变体，而是噪音——上限为 5。

用一行话写下计划，放在原型位置或文件顶部注释中：

> "设置页面的三个变体，通过 `?variant=` 切换，在现有 `/settings` 路由上。"

无论用户是否在场提出反对意见，这都适用。

### 2. 生成截然不同的变体

起草每个变体。每个变体都要满足：

- 页面的目的和它能访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）。
- 清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**——不同的布局、不同的信息层级、不同的主要交互方式，而不仅仅是不同的颜色。三个微调过的卡片网格不是 UI 原型，那是壁纸。如果两个草稿太相似，用明确的"不要使用卡片网格"指导重做其中一个。

### 3. 连接它们

在路由上创建一个单一的切换器组件：

```tsx
// 伪代码——适配项目的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形态 A（现有页面）：将现有的数据获取保留在切换器之上；只有渲染的子树根据变体切换。

对于子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载相同的切换器。

### 4. 构建浮动切换器

一个固定在屏幕底部中央的小型栏，包含三部分：

- **左箭头**——切换到上一个变体（循环）。
- **变体标签**——显示当前变体键值，如果变体导出了名称，也显示名称。例如 `B — 侧边栏布局`。
- **右箭头**——切换到下一个变体（循环）。

行为：

- 点击箭头更新 URL 搜索参数（使用框架的路由器——Next 的 `router.replace`、React Router 的 `navigate` 等），使变体可分享且重新加载稳定。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时，不要拦截方向键。
- 视觉上与页面区分开（例如高对比度胶囊、微妙阴影），让人一眼看出不是被评估的设计的一部分。
- 在生产构建中隐藏——通过 `process.env.NODE_ENV !== 'production'` 或等价检查控制，防止原型合并时将栏泄露给用户。

将切换器放在一个共享组件中，以便两种子形态都能复用。将它放在项目中共享 UI 所在的任何位置。

### 5. 交给用户

提供 URL（和 `?variant=` 键值）。用户会在方便时切换浏览。通常有趣的反馈是**"我想要 B 的头部搭配 C 的侧边栏"**——那才是他们真正想要的设计。

### 6. 捕获答案并清理

当一个变体胜出后，写下哪个胜出以及原因（提交消息、ADR、Issue，或原型旁边的 `NOTES.md`——如果用户在离线状态且尚未回应）。然后：

- **子形态 A**——删除落败的变体和切换器；将胜者整合到现有页面中。
- **子形态 B**——将胜出的变体提升为正式路由，删除一次性路由和切换器。

不要让变体组件或切换器留在代码库里。它们很快腐烂并迷惑下一个阅读者。

## 反模式

- **只在颜色或文案上不同的变体。** 那是微调，不是原型。真正的变体在结构上存在分歧。
- **变体之间共享太多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 则违背了初衷。每个变体应该能自由抛弃布局。
- **将变体连接到真实的可变操作。** 只读原型没问题。如果变体需要变更操作，指向一个存根——问题是"应该长什么样"，而非"后端是否能工作"。
- **直接将原型提升到生产。** 变体代码是在原型约束下编写的（没有测试、最小错误处理）。整合时重新正式编写。
