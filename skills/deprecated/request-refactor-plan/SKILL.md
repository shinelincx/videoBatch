name: request-refactor-plan
description: 通过用户访谈创建详细的重构计划（包含微小 commit），然后将其提交为 GitHub issue。当用户需要规划重构、创建重构 RFC，或将重构拆分为安全的渐进步骤时使用。
---

本 skill 将在用户需要创建重构请求时调用。请按照以下步骤执行。如果认为某些步骤不必要，可以跳过。

1. 请用户提供他们想要解决的问题的详细描述，以及可能的解决方案想法。

2. 探索仓库以验证他们的断言并理解代码库当前状态。

3. 询问他们是否考虑过其他方案，并向他们展示其他方案。

4. 就实现细节对用户进行访谈。要极其细致和 thorough。

5. 确定实现的确切范围。明确什么要改、什么不改。

6. 在代码库中检查该区域的测试覆盖情况。如果测试覆盖不足，询问用户的测试计划。

7. 将实现拆分为一个包含微小 commit 的计划。牢记 Martin Fowler 的建议："让每个重构步骤尽可能小，以便你始终能看到程序在运行。"

8. 创建一个包含重构计划的 GitHub issue。使用以下模板作为 issue 描述：

<refactor-plan-template>

## 问题陈述

开发人员面临的问题，从开发者的角度描述。

## 解决方案

问题的解决方案，从开发者的角度描述。

## Commit 计划

一份详细、冗长的实现计划。用通俗语言编写计划，将实现拆分为尽可能微小的 commit。每个 commit 都应让代码库保持在可运行状态。

## 决策文档

一份实现决策清单。包括：

- 将要构建/修改的模块
- 将要修改的模块的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体文件路径或代码片段。它们可能很快就会过期。

## 测试决策

一份测试决策清单。包括：

- 什么是好的测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似类型的测试）

## 超出范围

一份本次重构不涉及的内容的描述。

## 补充说明（可选）

关于重构的任何额外说明。

</refactor-plan-template>
