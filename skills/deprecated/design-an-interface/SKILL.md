# 设计界面

基于《软件设计哲学》中的"设计两次"原则：你的第一个想法不太可能是最好的。生成多个截然不同的设计，然后比较它们。

## 工作流

### 1. 收集需求

在设计之前，理解以下内容：

- [ ] 这个模块解决什么问题？
- [ ] 调用者是谁？（其他模块、外部用户、测试）
- [ ] 核心操作有哪些？
- [ ] 有什么约束？（性能、兼容性、现有模式）
- [ ] 什么应该隐藏在内部 vs 暴露出来？

问："这个模块需要做什么？谁会使用它？"

### 2. 生成设计（并行子 Agent）

使用 Task 工具同时启动 3 个以上子 agent。每个必须产生**截然不同**的方案。

```
每个子 agent 的 prompt 模板：

为以下模块设计一个界面：[模块描述]

需求：[已收集的需求]

此设计的约束：[为每个 agent 分配不同的约束]
- Agent 1："最小化方法数量 —— 目标最多 1-3 个方法"
- Agent 2："最大化灵活性 —— 支持多种用例"
- Agent 3："优化最常见场景"
- Agent 4："从[特定范式/库]中汲取灵感"

输出格式：
1. 界面签名（类型/方法）
2. 使用示例（调用者如何使用）
3. 此设计在内部隐藏了什么
4. 此方案的取舍
```

### 3. 展示设计

展示每个设计，包括：

1. **界面签名** - 类型、方法、参数
2. **使用示例** - 调用者实际如何使用
3. **它隐藏了什么** - 内部保持的复杂性

按顺序展示设计，以便用户在比较之前能充分理解每个方案。

### 4. 比较设计

展示所有设计后，从以下维度比较：

- **界面简洁性**：方法更少、参数更简单
- **通用 vs 专用**：灵活性 vs 聚焦
- **实现效率**：形态是否允许高效的内部实现？
- **深度**：小界面隐藏大量复杂性（好）vs 大界面搭配浅层实现（差）
- **正确使用容易度** vs **误用容易度**

以散文形式讨论取舍，不要用表格。突出设计分歧最大的地方。

### 5. 综合

通常最好的设计会结合多个方案的优点。问：

- "哪个设计最符合你的主要用例？"
- "其他设计中有没有值得采纳的元素？"

## 评估标准

来自《软件设计哲学》：

**界面简洁性**：方法更少、参数更简单 = 更容易学习和正确使用。

**通用性**：无需修改即可处理未来用例。但要警惕过度泛化。

**实现效率**：界面形态是否允许高效实现？还是会迫使笨拙的内部结构？

**深度**：小界面隐藏大量复杂性 = 深度模块（好）。大界面搭配浅层实现 = 浅层模块（避免）。

## 反模式

- 不要让子 agent 产生相似的设计 —— 强制根本性差异
- 不要跳过比较 —— 价值在于对比
- 不要实现 —— 这纯粹是关于界面形态
- 不要基于实现工作量来评估
