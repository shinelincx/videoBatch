# Interface Design（接口设计）

当用户想为选定的深化候选方案探索替代接口时，使用这个并行子 agent 模式。基于 "Design It Twice"（Ousterhout）——你的第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇——**module**、**interface**、**seam**、**adapter**、**leverage**。

## 流程

### 1. 定义问题空间

在派生子 agent 之前，为选定的候选方案编写面向用户的问题空间说明：

- 新接口需要满足的约束条件
- 它所依赖的依赖项，以及它们属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一个大致的示例代码草图来锚定约束——不是方案，只是让约束具体化的方式

将此展示给用户，然后直接进入步骤 2。用户在子 agent 并行工作时阅读和思考。

### 2. 派生子 agent

使用 Agent 工具并行派发 3 个以上的子 agent。每个子 agent 必须为深化模块生成**截然不同**的接口。

为每个子 agent 提供独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后是什么）。简报独立于步骤 1 中面向用户的问题空间说明。给每个 agent 不同的设计约束：

- Agent 1："最小化接口——目标最多 1-3 个入口点。最大化每个入口点的杠杆率。"
- Agent 2："最大化灵活性——支持多种用例和扩展。"
- Agent 3："为最常见的调用者优化——让默认情况尽可能简单。"
- Agent 4（如适用）："围绕跨接缝依赖的端口与适配器进行设计。"

在简报中同时包含 [LANGUAGE.md](LANGUAGE.md) 词汇和 CONTEXT.md 词汇，以便每个子 agent 能一致地使用架构语言和项目领域语言命名。

每个子 agent 输出：

1. 接口（类型、方法、参数——以及不变量、顺序、错误模式）
2. 使用示例，展示调用者如何使用它
3. 接缝背后隐藏的实现
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡——杠杆率高的地方和薄弱的地方

### 3. 展示与比较

依次展示设计，让用户能够消化每个方案，然后用文字进行比较。从**深度**（接口处的杠杆率）、**局部性**（变更集中在哪里）和**接缝位置**进行对比。

比较之后，给出你自己的推荐：你认为哪个设计最强以及原因。如果不同设计中的元素可以良好组合，提出混合方案。要有观点——用户想要明确的判断，而不是菜单。
