# Language（语言）

本 skill 每条建议使用的共享词汇。精确使用这些术语——不要替换为"component"、"service"、"API"或"boundary"。使用一致的语言是核心目标。

## 术语

**Module（模块）**
任何具有接口和实现的东西。刻意保持规模无关——同样适用于函数、类、包或跨层切片。
_避免使用_：unit、component、service。

**Interface（接口）**
调用者正确使用模块所需知道的一切。包括类型签名，也包括不变量、顺序约束、错误模式、所需配置和性能特征。
_避免使用_：API、signature（太窄——这些仅指类型层面的表面）。

**Implementation（实现）**
模块内部的内容——代码主体。与 **Adapter（适配器）** 不同：一个事物可以是小适配器大实现（Postgres 仓库），也可以是大适配器小实现（内存模拟）。当接缝是讨论主题时使用"适配器"；否则使用"实现"。

**Depth（深度）**
接口处的杠杆率——调用者（或测试）每单位接口学习成本能行使的行为量。当大量行为位于小接口背后时，模块是**深层**的。当接口复杂度几乎等于实现复杂度时，模块是**浅层**的。

**Seam（接缝）** _（来自 Michael Feathers）_
你可以在不就地修改的情况下改变行为的地方。模块接口所在的_位置_。将接缝放在哪里本身就是一个独立的设计决策，与接缝背后放什么无关。
_避免使用_：boundary（与 DDD 的有界上下文混淆）。

**Adapter（适配器）**
在接缝处满足接口的具体事物。描述_角色_（它填充什么槽位），而非实质（内部是什么）。

**Leverage（杠杆率）**
调用者从深度中获得的东西。每单位接口学习成本获得更多能力。一个实现在 N 个调用点和 M 个测试中获得回报。

**Locality（局部性）**
维护者从深度中获得的东西。变更、Bug、知识和验证集中在一处，而非分散在调用者中。修复一次，处处修复。

## 原则

- **深度是接口的属性，而非实现的属性。** 深层模块内部可以由小型、可模拟、可替换的部分组成——它们只是不属于接口的一部分。模块可以有**内部接缝**（对其实现私有，供自身测试使用）以及接口处的**外部接缝**。
- **删除测试。** 想象删除这个模块。如果复杂度消失了，模块没有隐藏任何东西（它是透传的）。如果复杂度在 N 个调用者中重新出现，模块就在发挥价值。
- **接口即测试面。** 调用者和测试跨越同一个接缝。如果你想测试_越过_接口，模块的形状可能不对。
- **一个适配器意味着假设的接缝。两个适配器意味着真实的接缝。** 除非有东西确实在接缝两侧变化，否则不要引入接缝。

## 关系

- **Module** 有且只有一个 **Interface**（向调用者和测试呈现的表面）。
- **Depth** 是 **Module** 的属性，针对其 **Interface** 衡量。
- **Seam** 是 **Module** 的 **Interface** 所在的位置。
- **Adapter** 位于 **Seam** 并满足 **Interface**。
- **Depth** 为调用者产生 **Leverage**，为维护者产生 **Locality**。

## 被拒绝的框架

- **深度作为实现行数与接口行数之比**（Ousterhout）：奖励填充实现。我们使用深度即杠杆率。
- **"Interface" 作为 TypeScript `interface` 关键字或类的公共方法**：太窄——这里的接口包含调用者必须知道的每个事实。
- **"Boundary"**：与 DDD 的有界上下文混淆。使用 **seam** 或 **interface**。
