# Diagnose

处理疑难 Bug 的一套规范。仅在明确有理由时才能跳过某个阶段。

探索代码库时，借助项目的领域词汇表建立相关模块的清晰心智模型，并检查你涉及区域的 ADR。

## 阶段 1 — 构建反馈循环

**这才是核心技能。** 其余都是机械操作。如果你有一个快速、确定性、agent 可运行的通过/失败信号来定位 Bug，你一定能找到根因——二分法、假设检验和插桩都只是在消费这个信号。如果没有这个信号，再怎么盯着代码看也无济于事。

在此阶段投入不成比例的努力。**要大胆，要有创造力，绝不轻言放弃。**

### 构建反馈循环的方法——大致按以下顺序尝试

1. **失败的测试**——在能触及 Bug 的任何层面编写：单元测试、集成测试、端到端测试。
2. **Curl / HTTP 脚本**——针对运行中的开发服务器。
3. **CLI 调用**——使用固定输入，将 stdout 与已知正确快照进行对比。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/控制台/网络进行断言。
5. **回放捕获的追踪。** 将真实的网络请求/负载/事件日志保存到磁盘；在隔离状态下通过代码路径回放。
6. **一次性测试框架。** 启动系统的最小化子集（一个服务，模拟依赖），通过单个函数调用触发 Bug 代码路径。
7. **属性测试 / 模糊测试循环。** 如果 Bug 是"偶尔输出错误"，运行 1000 个随机输入，寻找失败模式。
8. **二分法定位框架。** 如果 Bug 出现在两个已知状态之间（提交、数据集、版本），自动化"在状态 X 启动、检查、重复"，以便使用 `git bisect run` 定位。
9. **差异对比循环。** 将相同输入分别通过旧版本和新版本（或两种配置）运行，对比输出差异。
10. **HITL bash 脚本。** 最后手段。如果必须人工点击，用 `scripts/hitl-loop.template.sh` 来驱动操作，使循环保持结构化。捕获的输出反馈给你。

构建好正确的反馈循环，Bug 就已经解决了 90%。

### 持续改进循环本身

把循环当作一个产品来打磨。一旦有了循环，就问自己：

- 能不能更快？（缓存设置、跳过无关初始化、缩小测试范围。）
- 信号能不能更明确？（断言具体症状，而不是"没有崩溃"。）
- 能不能更确定？（固定时间、设置 RNG 种子、隔离文件系统、冻结网络。）

一个 30 秒的不稳定循环，几乎没有价值。一个 2 秒的确定性循环，才是调试的超级武器。

### 非确定性 Bug

目标不是得到一个干净的复现，而是**提高复现率**。将触发条件循环执行 100 次、并行化、增加压力、缩小时间窗口、注入休眠。50% 概率的 Bug 是可调试的；1% 则不行——持续提高复现率直到可以调试为止。

### 确实无法构建循环时

停下来并明确说明。列出你尝试过的方案。向用户请求：(a) 访问能复现的环境，(b) 捕获的产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或 (c) 允许在生产环境添加临时插桩。在没有循环的情况下，**不要**进入假设阶段。

在你确信拥有一个可靠的循环之前，不要进入阶段 2。

## 阶段 2 — 复现

运行循环。观察 Bug 的出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——而不是恰好发生在附近的其他失败。找错 Bug = 修错问题。
- [ ] 失败可以在多次运行中复现（或者，对于非确定性 Bug，复现率足够高以便调试）。
- [ ] 你已经捕获了确切的症状（错误信息、错误输出、慢耗时），以便后续阶段验证修复是否真正解决了问题。

在你成功复现 Bug 之前，不要继续下一步。

## 阶段 3 — 假设

在测试任何假设之前，生成 **3-5 个排好优先级的假设**。只生成单一假设会让你锚定在第一个看似合理的想法上。

每个假设都必须是**可证伪的**：陈述它做出的预测。

> 格式："如果 <X> 是根因，那么 <改变 Y> 会让 Bug 消失 / <改变 Z> 会让它更严重。"

如果你无法陈述预测，这个假设只是感觉——丢弃或打磨它。

**在测试前将排序列表展示给用户。** 他们通常拥有能立刻重新排序的领域知识（"我们刚部署了一个针对 #3 的变更"），或者知道他们已经排除的假设。这是一个低成本的检查点，能大幅节省时间。如果用户不在，不要阻塞——继续你的排序。

## 阶段 4 — 插桩

每个探测都必须映射到阶段 3 中的具体预测。**每次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**（如果环境支持）。一个断点胜过十条日志。
2. **有针对性的日志**——放在能区分假设的边界处。
3. 永远不要"记录所有东西然后 grep"。

**给每条调试日志打上唯一前缀标签**，例如 `[DEBUG-a4f2]`。最后清理时只需一次 grep 即可。不带标签的日志会残留；带标签的日志必死。

**性能分支。** 对于性能回归，日志通常是错误的工具。正确做法：建立基线测量（计时工具、`performance.now()`、性能分析器、查询计划），然后二分法定位。先测量，后修复。

## 阶段 5 — 修复 + 回归测试

在**修复之前**编写回归测试——但前提是存在**正确的接缝（seam）**。

正确的接缝是指测试能按照调用点实际发生的方式，触发**真实的 Bug 模式**。如果唯一可用的接缝太浅（只有一个调用者的测试，而 Bug 需要多个调用者触发；单元测试无法复制触发 Bug 的调用链），那儿的回归测试只会给出虚假的信心。

**如果不存在正确的接缝，这本身就是发现。** 记录下来。代码库的架构正在阻止你锁定这个 Bug。将此标记为下一阶段的任务。

如果存在正确的接缝：

1. 将精简后的复现转化为该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未精简的）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 事后复盘

声明完成前必须做到：

- [ ] 原始复现不再出现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或已记录接缝缺失）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀确认）
- [ ] 一次性原型已删除（或移至明确标记的调试位置）
- [ ] 在提交/PR 消息中陈述最终正确的假设——让下一个调试者学习

**然后问自己：什么能防止这个 Bug 再次发生？** 如果答案涉及架构变更（没有好的测试接缝、调用者纠缠不清、隐藏的耦合），将具体信息传递给 `/improve-codebase-architecture` skill。**在修复落地之后再提建议**，而不是之前——你现在拥有的信息比开始时多得多。
