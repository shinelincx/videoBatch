# Writing Agent Briefs（编写 Agent 简报）

Agent 简报是 Issue 移到 `ready-for-agent` 时发布在 GitHub Issue 上的结构化评论。它是离线 agent 工作的权威规范。原始 Issue 正文和讨论是上下文——agent 简报才是合约。

## 原则

### 持久性优于精确性

Issue 可能在 `ready-for-agent` 中停留数天或数周。在此期间代码库会变化。编写简报时要确保即使文件被重命名、移动或重构后仍然有用。

- **要**描述接口、类型和行为契约
- **要**命名 agent 应查找或修改的具体类型、函数签名或配置形状
- **不要**引用文件路径——它们会过时
- **不要**引用行号
- **不要**假设当前实现结构会保持不变

### 行为描述，而非过程描述

描述系统**应该做什么**，而非**如何实现它**。agent 会自行探索代码库并做出自己的实现决策。

- **好：** "`SkillConfig` 类型应接受一个可选的 `schedule` 字段，类型为 `CronExpression`"
- **差：** "打开 src/types/skill.ts 在第 42 行添加 schedule 字段"
- **好：** "当用户在不带参数运行 `/triage` 时，他们应该看到需要关注的 Issue 摘要"
- **差：** "在主处理函数中添加 switch 语句"

### 完整的验收标准

agent 需要知道自己何时完成。每个 agent 简报必须有具体、可测试的验收标准。每个标准应可独立验证。

- **好：** "运行 `gh issue list --label needs-triage` 返回经过初始分类的 Issue"
- **差：** "分诊应该正常工作"

### 明确范围边界

声明什么超出范围。这防止 agent 过度美化或对相邻功能做出假设。

## 模板

```markdown
## Agent Brief

**类别：** bug / enhancement
**摘要：** 一行描述需要做什么

**当前行为：**
描述现在发生了什么。对于 Bug，这是损坏的行为。
对于功能增强，这是新功能构建前的现状。

**期望行为：**
描述 agent 工作完成后应该发生什么。
具体说明边界情况和错误条件。

**关键接口：**
- `TypeName`——需要改变什么及为什么
- `functionName()` 返回类型——当前返回什么 vs 应该返回什么
- 配置形状——需要什么新的配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**超出范围：**
- 不应在此 Issue 中变更或处理的内容
- 看起来相关但实际独立的相邻功能
```

## 示例

### 好的 agent 简报（Bug）

```markdown
## Agent Brief

**类别：** bug
**摘要：** Skill 描述截断时在单词中间断开，产生损坏的输出

**当前行为：**
当 skill 描述超过 1024 个字符时，它会在恰好 1024 个字符处截断，
不考虑单词边界。这会产生在单词中间结束的描述
（例如 "Use when the user wants to confi"）。

**期望行为：**
截断应在 1024 个字符之前的最后一个单词边界处断开，
并追加 "..." 表示截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段——不需要类型变更，
  但填充它的验证/处理逻辑需要尊重单词边界
- 任何读取 SKILL.md frontmatter 并提取 description 的函数

**验收标准：**
- [ ] 1024 字符以下的描述保持不变
- [ ] 超过 1024 字符的描述在 1024 字符之前
      的最后一个单词边界处截断
- [ ] 截断后的描述以 "..." 结尾
- [ ] 包括 "..." 的总长度不超过 1024 字符

**超出范围：**
- 更改 1024 字符限制本身
- 多行描述支持
```

### 好的 agent 简报（功能增强）

```markdown
## Agent Brief

**类别：** enhancement
**摘要：** 添加 `.out-of-scope/` 目录支持以跟踪被拒绝的功能请求

**当前行为：**
当功能请求被拒绝时，Issue 以 `wontfix` 标签
和评论关闭。没有关于决策或推理的持久记录。
未来类似的请求需要维护者回忆或搜索
先前的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md`
文件中，捕获决策、推理和链接到所有请求该功能的 Issue。
在分诊新 Issue 时，应检查这些文件是否有匹配。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式——每个文件应有
  `# 概念名称` 标题、`**Decision:**` 行、`**Reason:**` 行，
  以及带有 Issue 链接的 `**Prior requests:**` 列表
- 分诊工作流应尽早读取所有 `.out-of-scope/*.md` 文件，
  并根据概念相似度匹配传入的 Issue

**验收标准：**
- [ ] 以 wontfix 关闭功能会创建/更新 `.out-of-scope/` 中的文件
- [ ] 文件包括决策、理由和已关闭 Issue 的链接
- [ ] 如果匹配的 `.out-of-scope/` 文件已存在，新 Issue 会被
      追加到其 "Prior requests" 列表，而不是创建重复文件
- [ ] 在分诊期间，检查并呈现现有 `.out-of-scope/` 文件，
      当新 Issue 匹配先前的拒绝时

**超出范围：**
- 自动匹配（由人类确认匹配）
- 重新打开先前被拒绝的功能
- Bug 报告（只有功能增强拒绝进入 `.out-of-scope/`）
```

### 差的 agent 简报

```markdown
## Agent Brief

**摘要：** 修复分诊 Bug

**做什么：**
分诊的东西坏了。看主文件然后修复它。
大约第 150 行的函数有问题。

**要变更的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这很差因为：
- 没有类别
- 模糊的描述（"分诊的东西坏了"）
- 引用会过时的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前行为与期望行为
