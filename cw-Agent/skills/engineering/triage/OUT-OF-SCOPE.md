# Out-of-Scope Knowledge Base（超出范围知识库）

仓库中的 `.out-of-scope/` 目录存储被拒绝功能请求的持久记录。它有两个用途：

1. **机构记忆**——为什么某个功能被拒绝，这样推理不会在 Issue 关闭后丢失
2. **去重**——当新 Issue 匹配先前的拒绝时，skill 可以呈现之前的决策而不是重新争论

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而非每个 Issue 一个文件。多个请求同一事物的 Issue 被分组到一个文件下。

## 文件格式

文件应以轻松、易读的风格编写——更像简短的设计文档而非数据库条目。使用段落、代码示例和示例来让推理清晰且对首次接触的人有用。

```markdown
# Dark Mode

本项目不支持 dark mode 或面向用户的主题。

## 为什么超出范围

渲染管道假设单一的颜色调色板定义在
`ThemeConfig` 中。支持多主题需要：

- 包裹整个组件树的主题上下文提供者
- 每个组件的主题感知样式解析
- 用户主题偏好的持久化层

这是一个重大的架构变更，与项目专注于
内容创作的定位不一致。主题是下游
嵌入或重新分发输出的消费者应关注的问题。

```ts
// 当前的 ThemeConfig 接口不支持运行时切换：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，在构建时解析
  fonts: FontStack;
}
```

## 先前的请求

- #42 — "添加 dark mode 支持"
- #87 — "为了无障碍的夜间主题"
- #134 — "Dark 主题选项"
```

### 命名文件

使用简短、描述性的 kebab-case 概念名称：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应足够让人在浏览目录时不需要打开文件就知道被拒绝的是什么。

### 编写理由

理由应该是实质性的——不是"我们不想要这个"而是为什么。好的理由参考：

- 项目范围或哲学（"本项目专注于 X；主题是下游关注点"）
- 技术约束（"支持这需要 Y，与我们的 Z 架构冲突"）
- 战略决策（"我们选择使用 A 而非 B，因为…"）

理由应该是持久的。避免引用临时情况（"我们现在太忙了"）——那些不是真正的拒绝，而是延期。

## 何时检查 `.out-of-scope/`

在分诊期间（步骤 1：收集上下文），读取 `.out-of-scope/` 中的所有文件。评估新 Issue 时：

- 检查请求是否匹配已有的超出范围概念
- 匹配基于概念相似度，而非关键词——"night theme" 匹配 `dark-mode.md`
- 如果匹配，向维护者呈现："这与 `.out-of-scope/dark-mode.md` 相似——我们之前拒绝是因为 [理由]。你仍然持相同看法吗？"

维护者可能：

- **确认**——新 Issue 被添加到现有文件的"先前请求"列表中，然后关闭
- **重新考虑**——超出范围文件被删除或更新，Issue 继续正常分诊
- **不同意**——Issue 相关但不同，继续正常分诊

## 何时写入 `.out-of-scope/`

仅在**功能增强**（不是 Bug）被拒绝为 `wontfix` 时。流程：

1. 维护者决定某个功能请求超出范围
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 如果是：将新 Issue 追加到"先前请求"列表
4. 如果否：创建新文件，包含概念名称、决策、理由和第一个先前请求
5. 在 Issue 上发布评论解释决定并提及 `.out-of-scope/` 文件
6. 以 `wontfix` 标签关闭 Issue

## 更新或删除超出范围文件

如果维护者改变了对先前拒绝概念的想法：

- 删除 `.out-of-scope/` 文件
- skill 不需要重新打开旧 Issue——它们是历史记录
- 触发重新考虑的新 Issue 继续正常分诊
