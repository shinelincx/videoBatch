## 领域感知

在探索代码库期间，同时查找现有文档：

### 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，则仓库有多个上下文。映射文件指向每个上下文的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

延迟创建文件——只有当有内容要写时才创建。如果不存在 `CONTEXT.md`，在第一个术语被确定时创建。如果不存在 `docs/adr/`，在需要第一个 ADR 时创建。

### 多上下文仓库处理策略

当仓库存在 `CONTEXT-MAP.md` 时，采用以下策略：

1. **上下文识别**：根据讨论内容自动推断所属上下文（通过关键词匹配），如果无法确定，则询问用户
2. **跨上下文引用**：当讨论涉及多个上下文时，使用完整的上下文限定术语（如 `Ordering.Order`、`Billing.Invoice`）
3. **术语映射表**：维护跨上下文的术语映射表，记录不同上下文之间相同术语的关系
4. **边界接口文档**：在 `CONTEXT-MAP.md` 中记录上下文之间的接口和交互模式
5. **术语冲突解决**：如果不同上下文使用相同术语但含义不同，在各自的 `CONTEXT.md` 中明确区分

## 在会话期间

### 对照词汇表提出挑战

当用户使用的术语与 `CONTEXT.md` 中现有语言冲突时，立刻指出。"你的词汇表将 'cancellation' 定义为 X，但你似乎指的是 Y——到底是哪个？"

### 打磨模糊语言

当用户使用模糊或过度重载的术语时，提出一个精确的标准术语。"你提到 'account'——是指 Customer 还是 User？这是两个不同的东西。"

### 术语定义质量标准

评估术语定义时，检查以下标准：

1. **清晰度**：定义简洁明了，避免模糊或歧义的语言
2. **准确性**：定义准确反映术语的实际含义，不夸大也不缩小
3. **完整性**：定义涵盖术语的核心特征，不遗漏重要信息
4. **一致性**：定义与代码实现和其他文档保持一致
5. **非实现性**：定义描述术语**是什么**，而不是它**如何实现**

当用户提出术语定义时，根据这些标准进行评估，并提供改进建议。

### 讨论具体场景

当讨论领域关系时，用具体场景进行压力测试。设计探测边界情况的场景，迫使用户精确定义概念之间的边界。

### 与代码交叉引用

当用户陈述某事物的工作方式时，检查代码是否一致。如果发现矛盾，指出来："你的代码取消了整个 Order，但你刚才说可以部分取消——哪个是对的？"

采用**分层扫描策略**：

1. **基础层**：使用正则表达式匹配术语的精确出现次数和上下文
2. **中间层**：识别代码中的类名、函数名、变量名与术语的对应关系
3. **高级层**：分析代码注释和文档字符串，检测术语的正确使用

**扫描配置**：
- 默认扫描核心业务代码目录（如 `src/`）
- 跳过测试文件和依赖目录
- 支持词干提取和同义词映射（例如 "tasks" 和 "task" 视为同一术语）
- 当发现冲突时，默认假设文档需要更新，但提示用户确认

**冲突解决策略**：当发现代码与文档不一致时，提供以下选项：
1. 更新文档以匹配代码
2. 更新代码以匹配用户意图
3. 进一步讨论澄清

### 内联更新 CONTEXT.md

当术语被确定时，立刻更新 `CONTEXT.md`。不要批量处理——在发生时即刻捕获。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

不要将 `CONTEXT.md` 与实现细节耦合。只包含对领域专家有意义的术语。

#### 草稿模式

采用**草稿模式**进行文档更新：

1. **内存草稿**：在会话期间将临时修改保存在内存中，不立即写入文件
2. **确认机制**：当用户确认术语定义最终确定后，才将其写入正式的 `CONTEXT.md` 文件
3. **会话持久化**：如果会话中断，草稿内容保存到临时文件中，以便后续会话继续
4. **差异预览**：在写入之前，向用户展示即将发生的变更，供用户最终确认

这样可以避免文档历史记录被大量中间版本污染，同时保持讨论过程的可追溯性。

### 谨慎提供 ADR

仅在以下三个条件都满足时才提议创建 ADR：

1. **难以逆转**——以后改变想法的成本很高
2. **缺乏上下文时会令人困惑**——未来的读者会疑惑"他们为什么这么做？"
3. **真正权衡后的结果**——存在真实的替代方案，你基于特定理由选择了其中一个

如果三个条件中任何一个不满足，跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。

#### ADR 审查和更新机制

建立以下 ADR 审查机制：

1. **状态检查**：定期检查 ADR 的 `Status` 字段，当发现状态为 `proposed` 的 ADR 超过一定时间未更新时，提示用户确认是否接受或拒绝
2. **依赖分析**：当更新或删除一个 ADR 时，检查是否有其他 ADR 引用它，并提示用户更新相关引用
3. **过时检测**：当代码实现发生重大变化时，检查相关的 ADR 是否仍然适用，如有必要提示用户更新或创建新的 ADR
4. **版本管理**：支持 ADR 的版本演进，当决策发生变化时，创建新的 ADR 并标记旧的为 `superseded`

### 与其他 Skill 的集成

`grill-with-docs` 应与其他 engineering skill 形成完整的工作流：

1. **前置依赖检查**：运行前检查是否已运行 `setup-matt-pocock-skills`，如果未运行则提示用户先执行配置

2. **交叉引用建议**：当讨论涉及架构问题时，建议用户运行 `improve-codebase-architecture` 或 `zoom-out` 进行深入分析

3. **后续行动建议**：当讨论产生需要跟踪的问题时，建议用户通过 `to-issues` 创建 issue，或通过 `to-prd` 创建产品需求文档

4. **测试验证建议**：当讨论的方案需要验证时，建议用户运行 `tdd` 进行测试驱动开发

完整工作流：问题诊断 → 方案讨论 → 文档更新 → 实施跟踪 → 测试验证
