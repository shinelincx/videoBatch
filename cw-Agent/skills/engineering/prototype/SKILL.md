# Prototype

原型是**一次性代码，用来回答一个问题**。问题的类型决定原型的形态。

## 选择分支

识别正在回答的问题——从用户的提示、周围代码判断，或者如果用户在线就直接询问：

- **"这个逻辑/状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个交互式终端应用，将状态机推入在纸上难以推理的边界情况。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在单个路由上生成多个截然不同的 UI 变体，通过 URL 搜索参数和底部浮动栏切换。

两个分支产生的产物截然不同——选错分支会浪费整个原型。如果问题确实模棱两可且联系不上用户，默认选择与周围代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部声明假设。

## 适用于两个分支的通用规则

1. **从第一天起就是一次性的，并明确标记。** 将原型代码放在实际使用位置附近（紧邻它为之原型化的模块或页面），以便上下文清晰——但命名要让读者一眼看出这是原型，不是生产代码。对于一次性 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **一条命令运行。** 无论项目使用什么任务运行器——`pnpm <name>`、`python <path>`、`bun <path>` 等。用户必须能不经思考就启动它。
3. **默认无持久化。** 状态存在于内存中。持久化是原型要_验证_的东西，而非它应该依赖的东西。如果问题明确涉及数据库，使用临时数据库或本地文件，并带上清晰的"原型——可以清空我"命名。
4. **跳过打磨。** 没有测试、没有错误处理（除非是让原型_可运行_所需的最小处理）、没有抽象。目的是快速学习然后删除它。
5. **暴露状态。** 每次操作后（逻辑分支）或每次变体切换时（UI 分支），打印或渲染完整的状态，让用户看到变化。
6. **完成后删除或吸收。** 当原型回答了它的问题后，要么删除它，要么将验证过的决策整合到正式代码中——不要让它烂在仓库里。

## 完成时

原型唯一值得保留的是_答案_。将它捕获到持久化的地方（提交消息、ADR、Issue，或原型旁边的 `NOTES.md`），连同它正在回答的问题一起。如果用户在旁边，捕获就是一次快速对话；如果不在，留下占位符以便他们（或你下次处理时）在删除原型之前填写结论。
