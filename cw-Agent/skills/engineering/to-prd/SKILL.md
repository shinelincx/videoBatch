此 skill 将当前对话上下文和代码库理解转化为 PRD。不要采访用户——只需综合你已经知道的内容。

Issue 追踪器和分诊标签词表应该已提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你还没有探索过仓库，先探索以了解代码库的当前状态。在 PRD 中全程使用项目的领域词汇表，并遵守你涉及区域的任何 ADR。

2. 勾勒出完成实现需要构建或修改的主要模块。积极寻找可以提取为深层模块的机会，这些模块可以独立测试。

深层模块（相对于浅层模块）是将大量功能封装在简单、可测试、很少变更的接口中的模块。

与用户确认这些模块是否符合他们的预期。与用户确认他们希望为哪些模块编写测试。

3. 使用下方模板编写 PRD，然后将其发布到项目 Issue 追踪器。应用 `ready-for-agent` 分诊标签——无需额外分诊。

<prd-template>

## 问题陈述

用户面临的问题，从用户的角度描述。

## 解决方案

问题的解决方案，从用户的角度描述。

## 用户故事

一个**长篇的**、编号的用户故事列表。每个用户故事应采用以下格式：

1. 作为一个 <角色>，我想要一个 <功能>，以便 <收益>

<user-story-example>
1. 作为一个手机银行客户，我想看到我的账户余额，以便我能做出更明智的消费决策
</user-story-example>

这个用户故事列表应该非常详尽，覆盖功能的各个方面。

## 实现决策

已做出的实现决策列表。可以包括：

- 将构建/修改的模块
- 将被修改的模块接口
- 来自开发人员的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快过时。

例外：如果原型产生的代码片段比文字更精确地编码了某个决策（状态机、reducer、schema、类型形状），将其内联在相关决策中并简短注明来自原型。裁剪为决策丰富的部分——不是工作演示，只是关键部分。

## 测试决策

已做出的测试决策列表。包括：

- 什么构成好的测试的描述（仅测试外部行为，而非实现细节）
- 将测试哪些模块
- 测试的先例（即代码库中类似的测试类型）

## 范围之外

对于此 PRD 来说超出范围的描述。

## 其他说明

关于功能的任何其他说明。

</prd-template>
