# To Issues

使用垂直切片（探测子弹）将方案拆解为可独立获取的 Issue。

Issue 追踪器和分诊标签词表应该已提供给你——如果没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

使用对话上下文中已有的内容。如果用户传入 Issue 引用（Issue 编号、URL 或路径）作为参数，从 Issue 追踪器获取并读取其完整正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索代码库，进行探索以了解代码的当前状态。Issue 标题和描述应使用项目的领域词汇表，并遵守你涉及区域的 ADR。

### 3. 起草垂直切片

将方案拆解为**探测子弹** Issue。每个 Issue 是一个薄垂直切片，端到端贯穿**所有**集成层，而不是某一层的水平切片。

切片可能是"HITL"或"AFK"。HITL 切片需要人工交互，例如架构决策或设计评审。AFK 切片可以在无需人工交互的情况下实现和合并。尽可能优先选择 AFK 而非 HITL。

<vertical-slice-rules>
- 每个切片交付一个狭窄但**完整**的路径，贯穿每一层（schema、API、UI、测试）
- 完成的切片可独立演示或验证
- 优先选择多个薄切片，而非少数厚切片
</vertical-slice-rules>

### 4. 询问用户

将建议的拆解方案以编号列表形式呈现。对于每个切片，展示：

- **标题**：简短描述性名称
- **类型**：HITL / AFK
- **被阻塞于**：哪些其他切片（如果有）必须先完成
- **覆盖的用户故事**：这处理了哪些用户故事（如果源材料中有）

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 依赖关系是否正确？
- 是否有任何切片应该合并或进一步拆分？
- 标记为 HITL 和 AFK 的切片是否正确？

迭代直到用户批准拆解方案。

### 5. 将 Issue 发布到 Issue 追踪器

对于每个批准的切片，在 Issue 追踪器上发布新 Issue。使用下方的 Issue 正文模板。这些 Issue 被视为已准备好供 AFK agent 处理，因此使用正确的分诊标签发布，除非另有指示。

按依赖顺序发布 Issue（阻塞者先行），以便你可以在"被阻塞于"字段中引用真实的 Issue 标识符。

<issue-template>
## 父 Issue

引用 Issue 追踪器上的父 Issue（如果源是现有 Issue，否则省略此部分）。

## 构建什么

此垂直切片的简洁描述。描述端到端行为，而非逐层实现。

避免具体的文件路径或代码片段——它们很快过时。例外：如果原型产生的代码片段比文字更精确地编码了某个决策（状态机、reducer、schema、类型形状），将其内联在此并简短注明来自原型。裁剪为决策丰富的部分——不是工作演示，只是关键部分。

## 验收标准

- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3

## 被阻塞于

- 引用阻塞工单（如果有）

或"无——可立即开始"（如果没有阻塞）。

</issue-template>

不要关闭或修改任何父 Issue。
