# QA 会话

运行交互式 QA 会话。用户描述他们遇到的问题。你进行澄清、在后台探索代码库以获取上下文，然后创建耐用、面向用户、使用项目领域语言的 GitHub issue。

## 对于用户提出的每个问题

### 1. 倾听并轻量澄清

让用户用自己的话描述问题。提出**最多 2-3 个简短澄清问题**，聚焦于：

- 他们期望什么 vs 实际发生了什么
- 复现步骤（如果不明显）
- 是一致出现还是偶发

不要过度追问。如果描述足够清晰可以提交，就继续。

### 2. 在后台探索代码库

在与用户交谈的同时，在后台启动一个 Agent（subagent_type=Explore）来了解相关区域。目标**不是**找到修复方法 —— 而是：

- 了解该区域使用的领域语言（检查 UBIQUITOUS_LANGUAGE.md）
- 理解该功能应该做什么
- 识别用户-facing 的行为边界

这些上下文有助于你写出更好的 issue —— 但 issue 本身**不应该**引用具体的文件、行号或内部实现细节。

### 3. 评估范围：单个问题还是需要拆分？

提交前，判断这是**单个问题**还是需要**拆分**为多个 issue。

需要拆分的情况：

- 修复涉及多个独立领域（例如"表单验证有问题 AND 成功消息缺失 AND 跳转 broken"）
- 存在明显可分离的关注点，不同人可以并行处理
- 用户描述的内容有多个不同的故障模式或症状

保持为单个问题的情况：

- 只有一处行为出错
- 所有症状都由同一个根本原因导致

### 4. 创建 GitHub issue

使用 `gh issue create` 创建 issue。不要先让用户审核 —— 直接创建并分享链接。

Issue 必须是**耐用的** —— 即使在重大重构之后仍然有意义。从用户角度编写。

#### 对于单个 issue

使用此模板：

```
## 实际现象

[描述用户经历到的实际行为，使用通俗语言]

## 期望现象

[描述期望的行为]

## 复现步骤

1. [具体的编号步骤，开发者可以跟随]
2. [使用代码库中的领域术语，不要使用内部模块名称]
3. [包含相关输入、flag 或配置]

## 补充信息

[来自用户或代码库探索的任何额外观察，帮助理解问题 —— 例如"这只有在使用 Docker 层时出现，文件系统层没有"—— 使用领域语言但不要引用文件]
```

#### 对于拆分（多个 issue）

按依赖顺序创建 issue（先创建阻塞项），这样你可以引用真实的 issue 编号。

对每个子 issue 使用此模板：

```
## 父 issue

#<父-issue-编号>（如果你创建了跟踪 issue）或"QA 会话期间报告"

## 问题描述

[描述这个具体的行为问题 —— 仅这一部分，不是整个报告]

## 期望现象

[针对这一部分的期望行为]

## 复现步骤

1. [针对此 issue 的具体步骤]

## 阻塞于

- #<issue-编号>（如果此 issue 在另一个修复之前无法测试）

或"无 —— 可以立即开始"（如果没有阻塞）。

## 补充信息

[与此部分相关的任何额外观察]
```

创建拆分时：

- **倾向多个精简 issue 而非少数臃肿 issue** —— 每个都应能独立修复和验证
- **诚实地标记阻塞关系** —— 如果 issue B 确实要等 issue A 修复后才能测试，就说明。如果它们独立，都标记为"无 —— 可以立即开始"
- **按依赖顺序创建 issue**，这样你可以在"阻塞于"中引用真实的 issue 编号
- **最大化并行性** —— 目标是让多人（或 agent）可以同时领取不同的 issue

#### 所有 issue 的通用规则

- **不要包含文件路径或行号** —— 这些会过期
- **使用项目的领域语言**（如果存在 UBIQUITOUS_LANGUAGE.md，请查看）
- **描述行为，不是代码** —— "同步服务无法应用 patch"而不是"applyPatch() 在第 42 行抛出"
- **复现步骤是必须的** —— 如果无法确定，询问用户
- **保持简洁** —— 开发者应该能在 30 秒内读完 issue

提交后，打印所有 issue 链接（并简要总结阻塞关系），然后问："下一个 issue，还是我们完成了？"

### 5. 继续会话

持续进行，直到用户说完成。每个 issue 是独立的 —— 不要批量处理。
